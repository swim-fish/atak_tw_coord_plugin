## How import routing works

Almost every file type rides the same **`ImportResolver`** framework (older deprecated subclasses are named `Import*Sort`; the current ones are `gov.tak.api.importfiles.Import*Resolver`). The shared pipeline is:

1. **`match(File)`** — each registered resolver decides whether it claims the file. This is `super.match()` (an **extension** gate built from the ctor's `_ext`) followed, for most formats, by a **content sniff** (read the first N bytes/chars or open the archive and look for a signature). Extension alone is rarely sufficient.
2. **`beginImport(File, Set<SortFlags>)`** — the chosen resolver copies/moves the file to its destination.
3. **`getDestinationPath(File)`** — computes the target as **`destinationDir + file.getName()`** (the ctor fixes `destinationDir`; the filename is the source filename, unchanged except for appending a missing extension). A few resolvers **override** this (DTED re-derives the path from header bytes; CoT returns the file itself).
4. **`FileSystemUtils.copyFile` / `renameTo`** — writes the file to the destination. A plain copy onto an existing path **overwrites in place**.
5. **`onFileSorted(...)`** — the base resolver broadcasts `Intent "com.atakmap.android.importexport.IMPORT_DATA"` carrying `contentType` / `mimeType` / `uri` (from `getContentMIME()`), and notifies registered `ImportListener`s. (CoT and iconset use their **own** broadcast actions instead — `IMPORT_COT`, `ADD_ICONSET`.)
6. **MapComponent / importer registration** — a `MapComponent` previously registered an `Importer` with `ImporterManager` keyed on the `(contentType, mimeType)` pair; that importer consumes the broadcast and ingests the file into its subsystem (spatial DB, raster catalog, CoT dispatcher, icon DB, or the DTED cell tree).

### The four conflict archetypes

Across all formats, "what happens on re-import" collapses to four patterns:

| Archetype | Identity key | Re-import behavior | Formats |
|---|---|---|---|
| **(a) filename / path overwrite** (file overlays) | destination path = `destinationDir/<file.getName()>` | silent overwrite-in-place; a different filename = a second parallel overlay; no content/UID dedup at the resolver layer | KML, KMZ, MVT, **Image** (geotagged JPEG → root), Data Package (resolver layer), iconset (on-disk zip) |
| **(b) catalog / DB-row keyed** (raster / elevation) | absolute file **path** in a catalog DB or the geographic **cell path** | path already cataloged & unchanged → **skip** (idempotent); changed → re-validate/update in place; different name → additional entry | GRG (`GRGs2.sqlite` catalog), **Layers / native imagery** (`imagery/` + `LayersMapComponent`), DTED (cell-tree layout *is* the catalog) |
| **(c) UID-keyed replace** (containers / icon sets) | UID parsed from a manifest/XML | same UID → old rows/dir removed then new inserted = in-place **replace**; content-hash dedup may **skip** identical content one layer up | iconset (`iconset.xml` UID), Data Package container (manifest UID + content-hash, see README §3) |
| **(d) CoT item-UID pipeline** | CoT `<event uid=…>` | same UID → existing `MapItem` **mutated in place** (last-received-wins; strict newer-wins only behind the dormant `ignoreLateCoTEvents` debug flag); different UID → new marker | CoT (`.cot`), and CoT payloads inside a Data Package (see README §2) |

## cot

**What it is.** A single Cursor-on-Target XML event (`<event>` + `<point>`) — a marker / map item.

**Flow.** `ImportResolver.match` accepts the `.cot` **FileFilter** first; then `ImportCotSort` reads the first **384 chars** and requires **BOTH** `"<event"` AND `"<point"` (`isCoT`) — a content sniff, not an extension-only check (a CoT-shaped file with a non-`.cot` extension is filtered out before the sniff). `beginImport` does **not** copy the file: `getDestinationPath` returns the file itself and the super-folder arg is empty `""` (so **no `cot/` folder** is created). It reads the XML into a String, broadcasts `Intent "…IMPORT_COT"` with extra `"xml"=<the XML>`, and if the source sits under `cache/atakdata/` it **`SECURE_DELETE`s** it so it isn't re-imported next launch. `ImportExportMapComponent.importCotReceiver` parses the event and `dispatchFrom()`s it into ATAK's internal CoT dispatcher → `CotImporterManager.importData` picks an importer by type → `MapItemImporter.importData` looks up an existing `MapItem` by event UID (`deepFindUID`); if found, `MarkerImporter` mutates it in place, else `createMarker(new Marker(uid))`. **Conflict = archetype (d):** same UID overwrites the same marker (last-received-wins; strict newer-wins only when the dormant `ignoreLateCoTEvents` debug flag is on); a different UID adds another. **See [README §2](./README.md#2-layer-a--item-uid-conflict) for the full item-UID analysis.**

**Evidence.** `javap ImportCotSort.<init>` → `ldc ".cot"`, `super(".cot","",…)` (empty folder), `sipush 384; newarray char`. `javap ImportCotSort#match` → `invokespecial ImportResolver.match` then `invokestatic isCoT(InputStream,[C)`. `javap ImportCotSort#isCoT(String)` → `ldc "<event"; String.contains; ifeq 39` / `ldc "<point"; String.contains; ifeq 39; iconst_1`. `javap ImportCotSort#getDestinationPath` → `aload_1; areturn` (returns the file itself). `javap ImportCotSort#beginImport` → `IMPORT_COT` intent, `putExtra("xml", …)`, `AtakBroadcast.sendBroadcast`, then `getCacheDir()`+`"atakdata"` `startsWith` check → `IOProviderFactory.delete(file, SECURE_DELETE)`. `javap MapItemImporter#findItem` → `getUID` → `MapGroup.deepFindUID`. `javap MarkerImporter#importMapItem` → `checkcast Marker`, `ifnonnull` (mutate via `setPoint`/`setMetaString`/`setTitle`) else `createMarker` (the only `new Marker(uid)`, guarded by `doNotRecreate`→`FAILURE`). *Two clone-vs-bytecode drifts (behavior unchanged):* in 5.7.0.5 the new-marker path routes through helper `createMarker(CotEvent,Bundle)` (not a direct `new Marker` at `:302/:306/:339`); cited clone line numbers are 5.5.1.10-only.

## datapackage

**What it is.** A `.zip` / `.dpk` Mission Package (Data Package) — a ZIP carrying a `MANIFEST/manifest.xml` plus content (CoT, attachments, overlays).

**Flow (two on-disk stages).** **Stage A (this resolver):** `ImportMissionPackageSort.match` runs `super.match` (extension `.zip`/`.dpk`); in **strict** mode it returns `MissionPackageExtractorFactory.HasManifest(file)` (a zip entry whose name `endsWith(MANIFEST_XML)`), in **non-strict** mode it requires `ZipUtils.isZip` **and** that no other non-MissionPackage sorter claims the zip ("a plain zip nothing else wants"). The ctor's destination folder = `TOOL_DATA_DIRECTORY + "/" + mission_package_folder` = **`tools/datapackage`**. `beginImport`: if a file of that name already exists it is `moveToTemp`'d then deleted (**filename overwrite**), `IMPORT_COPY` is force-added, and `super.beginImport` copies source → `tools/datapackage/<name>`. Parent `onFileSorted` reads `getContentMIME()=("Data Package","application/zip")` and broadcasts `IMPORT_DATA`. **Stage B (downstream, not this class):** `ImportReceiver` → `ImporterManager.findImporter("Data Package","application/zip").importData(uri)` hands off to `MissionPackageExtractor` / `ExtractMissionPackageTask`, which unzips into the datapackage tree (transfer staging `tools/datapackage/transfer`), reads the manifest, registers the package in the Data Package overlay, and fans its contents out to their own importers. **Conflict = archetype (a) at this resolver** (filename overwrite-in-place); **archetype (c) downstream** (manifest-UID + content-hash dedup in the MissionPackage subsystem). *Correction to the HackMD note:* `beginImport` does **not** itself reach the extractor — extraction is broadcast-dispatched one hop removed. **See [README §3](./README.md#3-layer-b--data-package-container-uid) for container UID + content-hash dedup.**

**Evidence.** `javap ImportMissionPackageSort#match` → `invokestatic MissionPackageExtractorFactory.HasManifest`; non-strict `ZipUtils.isZip` + `instanceof ImportMissionPackageSort` (skip self) + `ImportResolver.match`. ctor → `ldc "tools"` + `R$string.mission_package_folder` (`="datapackage"`). `javap #beginImport` → `getDestinationPath`, `IOProviderFactory.exists`/`isFile`, `FileSystemUtils.moveToTemp`, `deleteFile`, `SortFlags.IMPORT_COPY`, `super.beginImport`. `javap getContentMIME` → `ldc "Data Package"`, `ldc "application/zip"`. Class is `@Deprecated` (since 5.5, removeAt 5.8) in favor of `gov.tak.api.importfiles.ImportMissionPackageResolver` but still the resolver named in the task and present in 5.7.0.5.

## kml

**What it is.** A `.kml` vector overlay (placemarks, lines, polygons).

**Flow.** `ImportKMLSort.match`: `super.match` extension gate (`.kml`, fail-fast on mismatch), then a content sniff — `isKml` reads the first **2048 chars** and returns true iff `content.contains("<kml")` **OR** `content.matches("(?s).*<[^>]+:kml.*")` (literal `<kml` or namespaced `<ns:kml`). Destination = **`overlays/<file.getName()>`** (ctor passes `"overlays"`; base `getDestinationPath` = `new File(getItem("overlays"), name)`). `beginImport` copies the file there, **overwriting any same-named file in place** with no `exists()` precheck, no prompt, no rename-to-unique. `onFileSorted` then broadcasts `IMPORT_DATA{contentType="KML", mime=application/vnd.google-earth.kml+xml}` and notifies `ImportListener`s; the downstream KML importer (`KmlFileSpatialDb`, a `SpatialDbContentSource`) catalogs the file into a spatial feature DB keyed by file **path** and registers a `URIContentHandler`, surfacing it as a toggleable overlay in Overlay Manager. **Conflict = archetype (a):** path/filename, silent overwrite. *Verdict note (corrected):* the filesystem overwrite is proven from `ImportKMLSort`/`ImportResolver`; the "spatial-DB remove-then-readd" is a property of the **downstream** KML importer, **not** provable from these resolver classes — do not attribute it to them. `ImportKMLSort` is `@Deprecated` (removeAt 5.8, → `gov.tak.api.importfiles.ImportKMLResolver`). **See [README §4](./README.md#4-third-path--kmz--kml-overlay-data-packages-worked-example-cctvzip).**

**Evidence.** `javap ImportKMLSort.<init>` → `ldc ".kml"`, `ldc "overlays"`, `super(…)`. `javap #match` → `ImportResolver.match; ifne; iconst_0; ireturn` then `isKml`. `javap #isKml` → `sipush 2048; newarray char` … `ldc "<kml"; String.contains; ifne` ; `ldc "(?s).*<[^>]+:kml.*"; String.matches`. `javap getContentMIME` → `ldc "KML"`, `ldc "application/vnd.google-earth.kml+xml"`. `FileSystemUtils.OVERLAYS_DIRECTORY="overlays"`. `ImportResolver.getDestinationPath` → `new File(folder, fileName)`; `beginImport` COPY branch guards only `src.equals(dst)` then `copyFile` unconditionally (silent overwrite).

## kmz

**What it is.** A `.kmz` (zipped KML) — vector overlay, raster GRG, 3D model, or a mix.

**Flow (four resolvers, all keyed on `.kmz`; disambiguation is purely in `match()` — there is no `filterFoundResolvers` override).** **Plain/vector KMZ** is matched by `ImportKMZResolver` (current) / `ImportKMZSort` (`@Deprecated`) via three gates: (1) `super.match` ext `.kmz`; (2) `hasKML` walks the zip for a `*.kml` passing `isKml` (strict mode requires exactly one top-level `doc.kml`); (3) the decisive GRG-vs-overlay check — `KMZPackageImporter.getContentTypes(file)` must contain `"KML"` (else `Log.d("Skipping GRG KMZ")` → `false`, handed to the GRG resolver), then GDAL `ogr.Open` driver name must `contains("kml")`. `getContentTypes()` SAX-parses `doc.kml`: `<GroundOverlay>`→`"External GRG Data"`, `<Model>`→ModelImporter, `<Placemark>` geometry→`"KML"`. The **multi-payload** KMZ is matched by `ImportKMZPackageResolver`/`Sort` whose entire body is `return getContentTypes(file).size() > 1`. Destination = **`overlays/<file.getName()>`** (deterministic, no uniquifier, no hash/UID check). `beginImport` `copyFile` (or `renameTo`→`copyFile`) **overwrites in place**; `onFileSorted` broadcasts `IMPORT_DATA`. Routing: `"KML"`→`KmlFileSpatialDb` (OGR DB) catalogs/renders the overlay; `"KMZ"`→`KMZPackageImporter.importData` loops content types dispatching each (KML→OGR DB, GRG→GRG catalog, Model→ModelImporter). **Conflict = archetype (a):** same filename → overwrite + re-catalog; different filename → second independent overlay (no content-hash/KML-id dedup). **See [README §4](./README.md#4-third-path--kmz--kml-overlay-data-packages-worked-example-cctvzip).**

**Evidence.** `javap ImportKMZResolver.<init>` → `ldc ".kmz"`, `ldc "overlays"`, `FileSystemUtils.getItem`, `super(String,File,String,Drawable)`. `javap #match` → `super.match` → `hasKML` → `getContentTypes`.`contains("KML")`; else `Log.d "Skipping GRG KMZ:"`; then `ogr.Open` … `GetName().toLowerCase().contains("kml")`. `javap ImportKMZPackageSort#match` whole body → `getContentTypes; List.size; if_icmple`. `getContentMIME`: plain→`("KML","application/vnd.google-earth.kmz")`, package→`("KMZ",…)`. `getDestinationPath` → `new File(destinationDir, name)` (no uniquifier); `beginImport` → `copyFile`/`renameTo`+`copyFile` fallback. ## image

**What it is.** A **GPS-geotagged** JPEG photo (`.jpg` / `.jpeg`).

**Flow.** There **is** a dedicated resolver — `ImportJPEGSort` (and its new-API mirror `gov.tak.api…ImportJPEGResolver`), registered for `.jpg` and `.jpeg` (`ImportFilesTask` adds `new ImportJPEGSort(context, ".jpg", …)` and `".jpeg"`). `match` = `super.match` (extension gate) **AND** `isJpegExif(file)`, which requires readable EXIF **carrying a GPS fix** — `ExifHelper.getExifMetadata(file).getGPS() != null`. A plain, **un-geotagged** JPEG is therefore **not** claimed by this resolver. ## grg

**What it is.** A Gridded Reference Graphic — georeferenced raster imagery overlay. Many input shapes: `.ovr.sqlite` / `.ovr.mbtiles`, GeoTIFF (`ImageryFileType` path `"grg"`), GroundOverlay KML/KMZ, small (<256 MB) GDAL NITF, GeoPDF, non-terrain MBTiles, MCIA-GRG directory.

## dted

**What it is.** DTED elevation cells (`.dt0`/`.dt1`/`.dt2`/`.dt3`, loose or zipped in `.zip`/`.dpk`).

**Flow.** **Loose file:** `ImportDTEDSort.match` = `isDted(file.getName())` — lowercase then `endsWith(".dt3"|".dt2"|".dt1"|".dt0")`, **purely by extension** (the header is **not** read at match time). **Zip:** `ImportDTEDZSort.match` = `super.match` (`.zip`/`.dpk`) **AND** `hasDTED(file)` (opens the archive; matches if a cell-named entry `n/s/w/e…` is present, else header-validates via `readDtedFile`); `filterFoundResolvers` then clears the list and adds only itself, so a DTED zip is never also treated as a data package. **Destination is special — `getDestinationPath` is OVERRIDDEN** to re-derive the cell path from the DTED **header bytes** (not the source filename's directory): `<root>/DTED/<e|wXXX>/<n|sYY>.dtN`. `beginImport` `renameTo(src,dest)` (copy/delete fallback) overwrites the existing cell file. For zips, `onFileSorted`→`installDTED` unzips every cell, re-deriving each path under `DTED/` and streaming it out with a truncating `getOutputStream` (overwrite). **Registration:** purely filesystem — **no DB row, no spatial-DB/`layers.sqlite` insert**; the `DTED/` cell-tree layout **is** the catalog, scanned on demand by the native elevation reader. **Conflict = archetype (b), geographic cell path:** same lat/lon cell → same file path → last writer wins; the source filename is irrelevant (header decides the cell), so two differently-named files for the same cell collide and overwrite by design.

> *Refinements vs the HackMD note:* (1) the path is re-derived from the **header**, not the source filename, so a mislabeled file still lands at its true cell; (2) there is **no** catalog DB write — the directory tree itself is the catalog.

**Evidence.** `javap ImportDTEDSort#match` → `invokestatic isDted`; `isDted` → `ldc ".dt3"/".dt2"/".dt1"/".dt0"; endsWith`. `javap #getDestinationPath` → `invokestatic readDtedFile`; `readDtedFile` → `bipush 24; newarray char` (24 header bytes), builds basedir/filename from `b[19],b[13],b[14],b[11],b[4],b[5],b[6]`, `ldc "DTED"; getItem; new File(File,String)`. `javap #beginImport` → `File.equals` (no-op if same), `FileSystemUtils.renameTo`, `onFileSorted`. `javap ImportDTEDZSort#match` → `super.match` + `hasDTED` (`ZipFile.entries` + `containsDT` + `readDtedFile`); `filterFoundResolvers` → `List.clear`+`List.add(this)`; `onFileSorted` → `installDTED` → per-entry e/w+n/s path, `getOutputStream` truncating write. *Drift:* 5.5.1.10 ctor passes `FileSystemUtils.DTED_DIRECTORY`; 5.7.0.5 passes literal `"DTED"` — both = `getItem("DTED")` = `root+/DTED`. ## Methodology & sources

**Code-anchoring rule (project convention).** Every behavioral claim is anchored to **both** the `javap` `class#method` on the authoritative **5.7.0.5** `main.jar` **and** an upstream **5.5.1.10** permalink. **If the two disagree, the 5.7.0.5 SDK bytecode wins** and the doc says so. The permalinks confirm shape/contract; their **line numbers are valid for 5.5.1.10 only** (upstream has not published 5.7.0.x source).

**Disassembly command pattern.**
```sh
JAR=<ATAK_SDK_5_7_0_5>/main.jar
javap -classpath "$JAR" -p        <fqcn>          # signatures (existence / @Deprecated / ctor shape)
javap -classpath "$JAR" -p -c     <fqcn>          # bytecode (match/beginImport/getDestinationPath/onFileSorted)
javap -classpath "$JAR" -constants <fqcn>         # string constants (folder names, MIME, content types)
```
Representative classes disassembled: `ImportCotSort`, `ImportMissionPackageSort`, `ImportKMLSort`, `ImportKMZResolver`/`ImportKMZSort`/`ImportKMZPackageSort`, `ImportGRGSort`/`ImportGRGResolver`, `ImportDTEDSort`/`ImportDTEDZSort`, `ImportUserIconSetSort`, `ImportMVTSort`; plus the receivers/importers `ImportResolver`, `ImportExportMapComponent`, `MapItemImporter`/`MarkerImporter`, `MissionPackageExtractorFactory`, `KMZPackageImporter`, `GRGMapComponent`/`GRGDiscovery`/`PersistentRasterDataStore`/`LocalRasterDataStore`, `DTEDZCallback`, `IconsMapAdapter`/`UserIconDatabase`, `MvtSpatialDb`/`SpatialDbContentSource`/`WktMapComponent`; and the constant holder `FileSystemUtils`.

**Version-drift summary.** Bytecode (5.7.0.5) and clone (5.5.1.10) **agree on control flow** for every audited path. Known structural drifts (behavior unchanged):
- **Resolver base class moved.** `com.atakmap.android.importfiles.sort.ImportResolver` (5.5.1.10) → `gov.tak.api.importfiles.ImportResolver` (5.7.0.5). The legacy `Import*Sort` classes are `@Deprecated`/`@DeprecatedApi(removeAt 5.8)`; the current `gov.tak.api…Import*Resolver` replacements exist and are registered. Destination + conflict semantics are identical across the pair for every format.
- **CoT new-marker call shape.** 5.7.0.5 routes new-marker creation through a `createMarker(CotEvent,Bundle)` helper (with a `doNotRecreate`→`FAILURE` guard), not a direct `new Marker(uid)` at the clone's `:302/:306/:339`.
- **DTED dest constant.** 5.5.1.10 ctor passes `FileSystemUtils.DTED_DIRECTORY`; 5.7.0.5 passes literal `"DTED"` — both resolve to `getItem("DTED")`.
- **GRG dest constant.** 5.7.0.5 `ImportGRGResolver` calls `FileSystemUtils.getItem("grg")` in the ctor (passing a `File`) vs the legacy `Sort` passing the raw `"grg"` folder string — same resolved path.

**Per-format discrepancies / uncertain verdicts (honor these):**
- **CoT — corrected (behavior unchanged):** `match` requires **both** `<event` **and** `<point` in the first 384 chars (gated by the `.cot` FileFilter), and the destination is **not** a `cot/` folder — the folder arg is `""` and `getDestinationPath` returns the file itself; the only on-disk copy is the source, secure-deleted if under `cache/atakdata/`. Caveat: under `ignoreLateCoTEvents` it is last-by-event-time-wins, not unconditional last-received.
- **KML — conflict verdict corrected:** the filesystem path/filename overwrite is confirmed from `ImportKMLSort`/`ImportResolver`; the "spatial-DB remove-then-readd" is a property of the **downstream** KML importer and is **not provable** from the resolver bytecode — do not attribute it to the resolver.
- **MVT — citation corrected (substance unaffected):** class is `ImportMVTSort` (not `ImportMVTResolver`); `"overlays"` is an inline String constant, not an `OVERLAYS_DIRECTORY` field reference.
- **GRG — conflict-key naming:** the schema enum lacked a "file-path" option; the true key is the **absolute file path** (`queryCatalog(File)`), re-validated by file-tree currency (size/timestamp), not a content hash or UID. "geographic-cell-path" is the closest label.
- **Image — corrected → confirmed:** a dedicated resolver **does** exist. `ImportJPEGSort` (+ new-API `ImportJPEGResolver`) is registered for `.jpg`/`.jpeg` and gated on EXIF **GPS** (`isJpegExif` → `getGPS() != null`); folder is `null` → ATAK **root**; content `("JPEG Image","image/jpeg")` is consumed by the image-IPP importer (`image.ipp.ImportImageSort`). *(The earlier "no dedicated image importer" reading was an artifact of this format's analyze agent failing to return structured output; it was corrected by direct disassembly. Un-geotagged images / embedded images still ride iconset / GRG / attachment paths.)*
- **Layers — corrected → confirmed:** a dedicated resolver **does** exist. `ImportLayersSort` (registered in `ImportFilesTask`) has ext `null` + folder `imagery`, content-sniffs native imagery via `ImageryFileType` / `GeoPackage` / `MBTilesInfo` / `StreamingTiles` / `DatasetDescriptorFactory2`, and emits `("External Native Data","application/octet-stream")` consumed by `LayersMapComponent`. *(The earlier "no single layers importer" reading was likewise an analyze-agent failure, corrected by direct disassembly. It is a sibling of GRG: `imagery/` vs `grg/`.)*
